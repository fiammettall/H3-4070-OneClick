# 原理、使用与维护

本包把“选图、填动作、生成一个短镜头”放到本机网页里。你先准备好人物关键帧，再让 H3 补出中间运动，挑选满意的片段，最后去剪辑软件组装。平时不用修改 ComfyUI 节点。

**当前仍是待 RTX 4070 笔记本实机验收的预览版。** 安装、下载和界面检查通过，与“这台电脑已经生成合格视频”是两件事。真实验收记录见[目标机验收](目标机验收.md)，已有验证范围见[验证记录](../VALIDATION.md)。

## 从图片到视频，发生了什么

```mermaid
flowchart LR
    P[动作与镜头文字] --> E[4B 量化编码器]
    E --> C[ClipProj 条件适配]
    I[首帧与可选末帧] --> F[图像与视频条件节点]
    C --> H[量化 H3 与 Turbo LoRA 采样]
    F --> H
    H --> V[视频 VAE 解码]
    H --> A[音频 VAE 解码]
    V --> O[组合并保存短视频]
    A --> O
```

可以把文字编码器理解成“读懂指令的人”：4B 表示约 40 亿参数的模型规模，它把动作和镜头描述变成数字条件。ClipProj 把这种表示转换到 H3 可以使用的条件空间。它是本包采用较小编码器的适配环节，效果仍需看人物和动作是否准确。

首帧决定起点，可选的末帧帮助约束结束姿态。图像通过工作流中的条件节点和视频 VAE 参与约束。H3 从随机噪声出发，根据这些条件逐步生成压缩的视频和音频表示；视频、音频 VAE 再分别把它们还原成画面和声音，最后保存为媒体文件。

这不是把首图机械平移几次，也不是把原片逐帧换脸。**FL2VA 的首末帧约束不能承诺严格复刻原视频的动作轨迹、运镜或剪辑点。** 如果一个动作必须与原片完全对应，要另做参考视频编辑路线的测试；当前界面没有接入原视频换人流程。

## 为什么需要量化和 Turbo

| 组件 | 主要解决什么 | 需要接受的取舍 |
| --- | --- | --- |
| H3 W4A8 混合量化 | 用更紧凑的权重和相应计算格式减轻模型存储及运行压力。W4A8 通常指主要权重使用 4 位、部分激活使用 8 位，并不代表全部层都使用同一种精度。 | 可能影响细节和稳定性；实际速度还取决于显卡、算子、卸载和系统内存。文件变小不等于任意尺寸都能跑。 |
| 4B INT4 编码器与 ClipProj | 减轻理解提示词阶段的内存负担。 | 对复杂描述、人物细节和多角色关系的理解需要实际比较。 |
| FL2V Turbo LoRA | 让适配过的生成模型用较少采样步骤产生结果。 | 速度与画面质量存在取舍，不保证所有镜头都优于更多步骤的方案。 |

本包固定使用 `res_multistep / simple` 和 4 个调度步。**4 个调度步不应写成“官方 Euler 的 4 次模型求值（4 NFE）”。** 改采样器、步数或 LoRA 不是单纯换个数字，开发者应把它们作为一组配置重新验收。普通使用时保留默认值。

## 日常做一个镜头

第一次使用可以直接照[公开示例说明](../examples/README.md)上传配套测试图并复制提示词。示例提供可重复的输入和参数，真实输出要在自己的目标电脑生成。需要查看内部节点时，另可导入 `workflows/h3lite_4070_i2v.json`；日常简易页面使用的是对应 API 工作流。

1. 双击 `2_启动.cmd`，打开本机页面；上传清晰的单人物首图。首图比例尽量接近输出比例，先避免多人、复杂遮挡和非常大的动作。
2. 首测选 `640×352`、`56 帧`。当前为 24fps，名义时长约 2.33 秒。通过后再试 124 帧，约 5.17 秒。
3. 写清楚“人物做什么、镜头怎么动、哪些外观要保留”，点击一次生成，等待任务完成。
4. 看完整段视频，检查脸、头发、衣服、手和动作，再决定保留或重试。页面显示完成只代表生成任务返回了结果。

例如可以从这样的短动作开始：

> 固定镜头，中景。人物保持首图中的发型、制服和背景，轻轻转头看向镜头，眨一次眼，肩膀只有轻微起伏。光照稳定，不切镜头。

界面会为普通动作文字补上工作流所需的基础提示词结构，初学者不必先学习完整的结构化格式。末图可先不填；需要限制最后姿势时，再加入与首图外观一致的末图。

调试时每次只改一个因素，例如先改动作幅度，再改运镜。记录种子、提示词和首末图，便于比较。**相同种子有助于比较配置，不保证不同机器或软件版本生成逐字节相同的文件。**

OP 制作建议按镜头编号保存，例如 `S001_开场`、`S002_转头`。两台电脑各跑不同镜头或不同候选，采用相同角色设定与输出规格，挑选后统一剪辑。两台电脑不会合并显存。生成出的音轨也不会自动变成原 OP 的歌曲，配乐和对拍在剪辑阶段处理。

## 哪些目录要留好

| 目录或文件 | 内容与处理方式 |
| --- | --- |
| `input` | 上传的关键帧。需要复现任务时保留。 |
| `output` | 生成结果。确认满意后另存一份到项目素材目录。 |
| `user/jobs` | 任务、参数、输入登记与输出位置等记录。最好与相应素材一起备份。 |
| `logs`、`_state` | 安装状态、服务身份与排错记录。运行时不要随意编辑。公开日志前先检查隐私。 |
| `models` | 下载并校验的模型文件。安装器按锁文件检查和复用。 |
| `.cache` 与 `.partial` | 已下载的依赖、源码缓存和未完成下载。断网后继续安装需要这些文件，下载过程中不要清理。 |
| `runtime`、`engine`、`custom_nodes` | 本包独立 Python、ComfyUI 和节点源码。日常使用不用修改。 |
| `locks` | 软件版本、模型修订号、文件大小和 SHA-256 等身份信息。随意改动会破坏复现依据。 |

需要退出时使用 `4_停止服务.cmd`，等待完成后再移动目录或关机。停止运行中的生成会中断该任务，先保存已经完成的结果。

清理空间时先备份成片，确认没有安装或下载运行，再决定清理缓存。删除缓存后，下一次安装可能需要重新下载；删除输入或任务记录可能影响追溯。不要通过删除全部目录来处理单个下载错误。

## 出错后从哪里看

| 现象 | 先做什么 |
| --- | --- |
| 断网、超时、下载未完成 | 保留目录，再运行 `1_安装或继续下载.cmd`；先看最新安装日志。 |
| SHA-256 校验失败 | 看日志中的隔离文件路径和下载来源；损坏文件会保留为 `.bad-时间戳`，再次继续安装会重新下载。不要关闭证书校验绕过问题。 |
| 页面连接不上或一直等待服务 | 运行 `3_检查环境.cmd`，查看 `logs` 中对应服务日志；核对是否已经完整安装、端口是否被其他程序占用。 |
| 缺模型、缺节点、依赖冲突 | 保存完整错误文字，回到安装入口核验固定版本；不要先随意升级 torch 或复制其他整合包的节点。 |
| 显存或系统内存不足 | 先保存其他工作并关闭暂时不用的游戏等程序，重启本包服务后用 56 帧首测。记录报错与资源峰值，避免连续排入更长任务。 |
| 有文件但画面变形、动作不对 | 保留该候选及参数，简化动作或换一致性更好的首末图。文件生成成功不能代替视觉验收。 |

给别人排错时，先提供阶段、错误文字、版本和最小复现步骤。原始角色图片、私人视频、凭据与全部任务记录不是默认必需材料。

## 升级与回退

先停止服务并备份 `input`、`output`、`user/jobs`，记录当前包版本和锁文件。新版本解压到**另一个独立目录**，完成安装，再用同一张测试图和同一组参数检查。通过后才把日常使用入口切过去；旧目录暂时保留，出问题可以停止新服务，再从旧目录启动。

升级应同时核对源码提交、模型、编码器、ClipProj、LoRA、依赖和工作流，不建议初学者在旧目录里随手点“全部更新”。开发过程也不应把清理用户素材作为升级步骤。需要复用模型时，只复用与新锁文件大小和 SHA-256 相符的文件，交给安装器重新核验。

模型、软件和素材的许可分别保留，参见[第三方说明](../THIRD_PARTY_NOTICES.md)。公开分享时不要把私人输入、生成历史或模型缓存打进部署包。
